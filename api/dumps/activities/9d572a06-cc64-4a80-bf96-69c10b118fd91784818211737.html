Front End

Le back-end peut sembler très abstrait, mais il devient plus clair lorsque nous l'expliquons en termes de front-end ! Pour simplifier un peu, le front-end correspond aux parties d'une page Web avec lesquelles un visiteur peut interagir.

Divers outils et frameworks peuvent être utilisés pour créer une page Web, mais, à la base, le front-end est composé de JavaScript, CSS, HTML et d'autres assets statiques, tels que des images ou des vidéos. Les assets statiques sont des fichiers qui ne changent pas. Lorsqu'un visiteur accède à une page Web, ces ressources sont envoyées à son navigateur.

Visiter un simple site web, c'est comme se faire livrer dans un restaurant : on passe une commande pour notre repas, et une fois qu'il nous est livré, on l'a entièrement en notre possession. Dans cette analogie, nous pouvons considérer le front-end comme tout ce qui est déposé avec la livraison : les contenants, les ustensiles et la nourriture elle-même.

Vous entendrez parfois le développement frontal appelé développement côté client. Notre instinct peut être de considérer le client comme le visiteur humain ou l'utilisateur d'un site Web, mais lorsque nous nous référons au client dans le développement Web, nous faisons généralement référence au demandeur de contenu non humain. Dans le cas de la visite d'un site Web, le client est le navigateur, mais dans d'autres circonstances, un client peut être une autre application, un appareil mobile ou même un appareil « intelligent » !

Alors que le front-end est la partie du site Web qui parvient au navigateur, le back-end se compose de tous les processus et données en arrière-plan qui font fonctionner un site Web et envoient des ressources aux clients.

Le Backend

Le Web server

Nous avons dit que le front-end se compose des informations envoyées à un client afin qu'un utilisateur puisse interagir avec un site Web, mais d'où proviennent ces informations ? La réponse est un serveur Web.

Un serveur Web est un processus exécuté sur un ordinateur qui écoute les demandes d'informations entrantes sur Internet et renvoie les réponses. 

Chaque fois qu'un utilisateur accède à un site Web sur son navigateur, le navigateur adresse une requête au serveur Web de ce site Web. À savoir que chaque site Web a au moins un serveur Web. 

Une grande entreprise comme Facebook possède des milliers d'ordinateurs puissants exécutant des serveurs Web dans des installations situées partout dans le monde qui écoutent les demandes, mais nous pourrions également exécuter un simple serveur Web à partir de notre propre ordinateur !

Le format spécifique d'une demande (et la réponse qui en résulte) est appelé le protocole. Vous connaissez peut-être le protocole utilisé pour accéder aux sites Web : HTTP. Lorsqu'un visiteur accède à un site Web sur son navigateur, de la même manière que l'on passe une commande de plats à emporter, il effectue une requête HTTP pour les ressources qui composent ce site

Pour les sites Web les plus simples, un client fait une seule demande. Le serveur Web reçoit cette demande et envoie au client une réponse contenant tout ce dont il a besoin pour afficher le site Web. C'est ce qu'on appelle un site Web statique. Cela ne signifie pas que le site Web n'est pas interactif. Comme pour les actifs statiques individuels, un site Web est statique car une fois ces fichiers reçus, ils ne changent ni ne bougent. 

Un site Web statique peut être un bon choix pour un site Web personnel simple avec une courte biographie et des photos de famille. Cependant, un utilisateur naviguant sur Twitter souhaite accéder au nouveau contenu au fur et à mesure de sa création, ce qu'un site Web statique ne pourrait pas fournir.

Un site Web statique, c'est comme commander des plats à emporter, mais les applications Web modernes, c'est comme manger en personne dans un restaurant assis. Un client du restaurant peut commander des boissons, des plats différents, faire des substitutions ou poser des questions au serveur. Pour atteindre ce niveau de complexité, un back-end tout aussi complexe est nécessaire.

Contenu Dynamique

Lorsque nous mangeons au restaurant, nous commandons selon nos goûts, faisons des échanges avec le personnel, customiser nos plats, etc. le résultat est une expérience culinaire unique pour nous. 

En dehors de cela, il se passe beaucoup de choses dans les coulisses pour faire fonctionner un restaurant : les ingrédients sont commandés auprès des fournisseurs, de nouveaux menus sont conçus et les horaires des employés sont créés. De même, pour créer une application Web qui fonctionne correctement, le back-end fait bien plus que simplement envoyer des ressources aux navigateurs.

L'ensemble de la logique de programmation nécessaire pour fournir un contenu dynamique à un client, gérer la sécurité, traiter les paiements et d'autres tâches est appelé << serveur d'applications >>. Le serveur d'application peut être responsable de tout, de l'envoi d'un e-mail de confirmation après un achat à l'exécution des algorithmes compliqués qu'un moteur de recherche utilise pour nous donner des résultats de nos recherches.

API

Lorsqu'un utilisateur navigue vers un produit spécifique à vendre sur un site de e-commerce, le prix indiqué pour ce produit est stocké dans une base de données

Lorsqu'il l’utilisateur l’achète, la base de données devra être mise à jour avec l'inventaire correct pour ce type de produit.En fait, une grande partie de ce que le back-end implique est la lecture (READ), la mise à jour (UPDATE) ou la suppression (DELETE) d'informations stockées dans une base de données.

Afin d'avoir des moyens cohérents d'interagir avec les données, un back-end inclura souvent une API Web. API signifie Application Programming Interface … une API Web est un ensemble de méthodes ou de règles prédéfinies pour interagir avec les données d'une application Web Souvent via un cycle HTTP requête-réponse.

Contrairement aux requêtes HTTP qu'un client effectue lorsqu'un utilisateur navigue vers l'URL d'un site Web, ce type de requête indique comment il souhaite interagir avec les données d'une application Web (créer de nouvelles données, lire des données existantes, mettre à jour des données existantes ou supprimer des données existantes) , et il reçoit des données en retour en réponse.

Reprenons l'exemple d'un achat en ligne, mais cette fois, nous allons imaginer comment l'API Web de l'application pourrait être utilisée. Lorsqu'un utilisateur appuie sur le bouton pour soumettre une commande, cela déclenchera une demande pour l'envoyer vers une vue différente du site Web, une page de confirmation de commande, mais une demande supplémentaire sera déclenchée depuis le front-end, invisible pour l'utilisateur, à l'API Web afin que la base de données puisse être mise à jour avec les informations de la commande.

Certaines API Web sont ouvertes au public. Data.gouv.fr, par exemple, dispose d'une API que d'autres développeurs peuvent utiliser pour accéder à certaines des données stockées par l’état. D'autres ne sont utilisés que par l'application Web en interne.

 L' Authentification et l' Autorisation.

Deux autres concepts que nous voudrions que notre logique côté serveur gère sont l'authentification et l'autorisation.

L'authentification est le processus de validation de l'identité d'un utilisateur.Une technique d'authentification consiste à utiliser des connexions avec des noms d'utilisateur et des mots de passe. Ces informations d'identification doivent être stockées en toute sécurité dans le back-end d'une base de données et vérifiées à chaque visite. 

Les applications Web peuvent également utiliser des ressources externes pour l'authentification. Vous vous êtes probablement connecté à un site Web ou à une application à l'aide de vos informations d'identification Facebook, Google ou Github ; c'est aussi un processus d'authentification. SSO

L' Autorisation contrôle quels utilisateurs ont accès à quelles ressources et actions. Certaines vues de l'application, comme la page permettant de modifier un profil personnel sur les réseaux sociaux, ne sont accessibles qu'à cet utilisateur. D'autres activités, comme la suppression d'un message, sont souvent restreintes de la même manière.

Lors de la création d'un back-end d'application Web robuste, nous devons intégrer à la fois l'authentification (Qui est cet utilisateur ? Sont-ils ceux qu'ils prétendent être ?) et l'autorisation (Qui est autorisé à faire et à voir quoi ?) dans notre logique côté serveur. pour nous assurer que nous créons un contenu sécurisé, personnalisé et dynamique.
