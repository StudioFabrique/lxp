Définition. La cohésion mesure à quel point les éléments d’un module (classe, package, service) poursuivent un même but. Plus la cohésion est forte, plus le module est compréhensible, testable et changeable sans effet domino.

Pourquoi c’est critique.

  • Rend le code prévisible : on devine où implémenter une règle.
  • Réduit la surface de changement : une évolution métier touche un seul endroit.
  • Favorise la qualité des tests : scénarios centrés sur un comportement bien délimité.

Signaux de faible cohésion.

  • “Fourre-tout” : un même module gère des responsabilités sans lien naturel.
  • Noms vagues : Utils, Manager, Common, Helper.
  • Modifications hétérogènes dans un même fichier au fil du temps (journal de commits dispersé).

Heuristiques pour l’améliorer.

  • Nommer par intention (nom = capacité métier), pas par technologie.
  • Regrouper par capabilités (use-cases) plutôt que par couches techniques uniquement.
  • En DDD : aligner les modules sur des agrégats ou bounded contexts.
  • Scinder quand un module répond à plus d’une question “À quoi ça sert ?”.
