Nous savons tous qu'écrire du code de qualité est important et que la refactorisation nous oblige à concevoir des méthodes plus concises, réutilisables et auto-documentées.

Certains affirment que les commentaires sont à proscrire et qu'il faut viser un code auto-commenté. Quoi qu'il en soit, chacun devrait s'efforcer de produire un code de qualité, facile à lire, à comprendre et à maintenir. Mais le code ne révèle pas tout. Imaginons que vous ayez commencé à travailler sur un nouveau projet logiciel déjà en cours. Les éléments principaux sont en place et certaines fonctionnalités sont déjà implémentées. 

Vous démarrez votre machine de développement, téléchargez le code depuis le système de gestion de versions et l'importez dans votre environnement de développement. Que faites-vous ensuite et comment commencez-vous à être productif ? Si personne n'a le temps de vous expliquer le code source, vous pouvez commencer à formuler vos propres hypothèses en fonction de vos connaissances limitées du projet, du domaine métier, de vos attentes quant à la manière dont l'équipe développe le logiciel et de votre connaissance des technologies utilisées.

Par exemple, vous pourriez déduire certaines informations sur l'architecture globale du système logiciel en observant la manière dont le code source est structuré en sous-projets, répertoires, packages, espaces de noms, etc. 

Le code ne reflète pas l'intention de la conception.

Une analyse plus approfondie du code permettra de confirmer ou d'infirmer vos hypothèses initiales, mais soulèvera probablement de nombreuses questions. Vous comprenez peut-être le fonctionnement global du système, mais vous ignorez certains points :

- Comment le système s'intègre à l'architecture existante.

- Pourquoi les technologies utilisées ont-elles été choisies ?

- La structure globale du système.

- Où les différents composants sont déployés lors de l'exécution et comment ils communiquent.

- Comment la couche web « sait » où trouver la couche intermédiaire.

- Quelle approche de la journalisation, de la configuration, de la gestion des erreurs, etc., a été adoptée et est-elle cohérente dans l'ensemble du code ?

- Si des modèles et principes communs sont utilisés dans l'ensemble du code.

- Comment et où ajouter de nouvelles fonctionnalités.

- Comment la sécurité a été mise en œuvre à tous les niveaux de la pile technologique.

- Comment la scalabilité est assurée.

- Comment fonctionnent les interfaces avec les autres systèmes. 

- etc...

Informations complémentaires

Pour tout système logiciel, une couche d'informations supplémentaire, située au-dessus du code, apporte des réponses à ce type de questions et bien d'autres.

Ces informations complètent le code et doivent être consignées, par exemple dans une documentation complémentaire concise, afin de préciser ce que le code lui-même ne révèle pas. Le code donne des indications, mais il ne révèle pas tout.
