La technique consiste à créer quatre niveaux de diagrammes, chacun zoomant davantage sur le système :

Niveau 1: Diagramme de Contexte Système

La vue « argumentaire éclair »

  • Question : “Quel est le système, pour qui et avec quoi il interagit ?”

  • But : Montrer comment le système s'insère dans le monde environnant.

  • Éléments : Le système lui-même (une boîte centrale), les utilisateurs (personnes) et les systèmes externes avec lesquels il interagit.

  • Focus : Relations et périmètre, pas de détails techniques.

  • Contenu attendu :

    • Le “Software System” au centre (le produit)

    • Les personnes (acteurs) qui l’utilisent

    • Les systèmes externes (paiement, SMS, labo, SI existant, etc.)

    • Les relations principales (qui parle à qui, pour quoi)

    • Public : Tout le monde (parties prenantes, chefs de produit, utilisateurs).

  • Ce diagramme montre votre système comme une seule boîte. Il se concentre sur le qui et le quoi. Qui utilise le système ? Avec quels systèmes externes (comme un fournisseur LLM) communique-t-il ? Il ignore tous les détails techniques de mise en œuvre.

Niveau 2 : Diagramme de Conteneurs

La vue « planification des infrastructures »

  • Question : “En quoi le système est-il découpé à haut niveau, et comment ces morceaux communiquent ?”

    • Un “container” ici n’est pas forcément Docker : c’est une unité déployable/exécutable ou un stockage significatif (web app, mobile app, API, service, database…).

  • But : Décomposer le système en ses grandes unités techniques.

  • Définition d'un conteneur : Une application ou une banque de données séparément déployable (ex: application web, base de données, application mobile, microservice).

  • Focus : Choix technologiques et communication entre conteneurs.

  • Contenu attendu :

    • Applications (web, mobile, back-office)

    • API / services / jobs

    • Bases de données / files / caches

    • Protocoles/technos importantes (HTTP, gRPC, MQ, SQL…)

    • Relations entre conteneurs

  • Public : Architectes, Développeurs, DevOps.

Maintenant, zoomons. Un « conteneur » est une unité déployable séparément. C’est ici que nous voyons votre pile technologique moderne en action. Nous montrons l'application Web, les microservices, les files d'attente SQS, la base de données relationnelle et la base de données vectorielle. Il montre comment les données circulent entre ces principaux blocs de haut niveau

Niveau 3 : Diagramme de Composants

La vue « équipe de développement »

  • Question : “À l’intérieur d’un container, quels composants structurent le code et les responsabilités ?”

    • Un “component” = un bloc logique cohérent (Controller, Service applicatif, Repository, Adapter, etc.), selon le style architectural (Clean/Hexa, Layered, DDD…).

  • Contenu attendu :

    • Composants et responsabilités (phrases courtes)

    • Interfaces majeures (API internes, ports/adapters)

    • Dépendances entre composants

  • But : Zoomer à l'intérieur d'un conteneur pour montrer ses composants internes

  • Définition d'un composant : Un regroupement de fonctionnalités liées derrière une interface propre, s'exécutant dans le même processus que le conteneur.

  • Public : Développeurs.

En zoomant sur un micro-service spécifique – disons le service de requête AI – nous voyons ses composants internes. Nous voyons le générateur d'intégration, le Vector Retriever et le LLM Prompt Builder. Cela aide un développeur à comprendre les responsabilités internes du code.

Niveau 4 : Diagramme de Code

La vue "implémentation"

  • Question : “Quelle est la structure détaillée du code ?”

    • Souvent inutile en documentation d’architecture : le code et l’IDE font déjà ce travail. Utile uniquement pour expliquer un pattern complexe, une partie critique, ou pour un enseignement très “design”.

  • But : Montrer l'implémentation d'un composant (souvent via un diagramme de classes UML).

  • Note : Ce niveau est souvent considéré comme optionnel, car les détails se trouvent déjà dans le code.

  • Public : Développeurs.

C'est le niveau des classes et des objets. Dans le monde moderne, nous dessinons rarement cela manuellement ; nous laissons généralement le code être la source de vérité ou le générons automatiquement si nécessaire.

Ce que C4 ne cherche pas à faire

  • C4 ne remplace pas tous les artefacts d’architecture.

  • Il ne décrit pas en détail le comportement à l’exécution.

  • Il ne modélise pas la topologie de l’infrastructure ni les règles de sécurité réseau.

  • Il ne supprime pas le besoin de diagrammes de séquence ou d’ADR.

Ce qu’il apporte, en revanche, c’est une ossature structurelle stable — un modèle mental partagé sur lequel les autres diagrammes peuvent s’appuyer.
