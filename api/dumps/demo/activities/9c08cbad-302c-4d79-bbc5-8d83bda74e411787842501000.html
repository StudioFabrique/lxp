WAI-ARIA : c’est quoi, pourquoi, quand et comment

WAI-ARIA (Accessible Rich Internet Applications) est un standard du W3C qui ajoute des rôles, états et propriétés aux éléments pour que les aides techniques (lecteurs d’écran, etc.) comprennent les noms, rôles et états des composants, surtout quand ils sont dynamiques (menus, modales, onglets, accordéons, toasts…).

> Règle n°1 d’ARIA : si un élément HTML natif suffit, n’utilise pas ARIA. (ARIA n’ajoute ni focus, ni comportement clavier.)

Pourquoi ARIA ?

  • Widgets non natifs : tu crées un menu, un onglet, un switch custom → ARIA décrit ce que c’est et dans quel état il est.
  • Mises à jour dynamiques : zones qui changent sans rechargement → aria-live annonce les changements.
  • Points de repère (landmarks) : structurent la page pour la navigation rapide (role="navigation", main, contentinfo, etc.).

Quand l’utiliser (et quand éviter)

  • ✅ À utiliser si :

    • Tu as un composant custom où l’HTML natif ne couvre pas le besoin (ex. faux bouton en <div> → mieux : vrai <button>, sinon ajouter rôle + clavier).
    • Tu dois annoncer un état (ouvert/fermé, sélectionné, coché, occupé…) ou une relation (bouton ↔ panneau).

  • ❌ À éviter si :

    • Un élément natif existe (<button>, <details>, <summary>, <dialog>…).
    • Tu t’en sers pour “réparer” un HTML cassé (ex. role="button" sur un <div> sans gestion clavier).

Les grandes familles ARIA

1) Rôles

  • Landmarks : banner, navigation, main, complementary, contentinfo.
  • Widgets : button, checkbox, switch, tab, tablist, tabpanel, menu, menuitem, dialog, alertdialog, combobox, slider, spinbutton.
  • Document : article, heading (avec aria-level), list, listitem.
  • Live regions : alert, status, log, progressbar.

2) États & propriétés (exemples utiles)

  • Visibilité/structure : aria-hidden, aria-controls
  • Ouverture/fermeture : aria-expanded
  • Sélection/pression : aria-selected, aria-pressed, aria-checked
  • Nom & description : aria-label, aria-labelledby, aria-describedby
  • Navigation : aria-current
  • Feedback : aria-live, aria-busy, aria-invalid

Accessible Name & relations (très important)

  • Le nom accessible d’un contrôle provient, dans l’ordre, de aria-labelledby, puis de aria-label, puis du contenu texte.
  • aria-describedby ajoute un complément (aide/erreur), mais ne remplace pas le nom.
  • Les relations (aria-controls, aria-labelledby) reposent sur des IDs valides → pas d’IDs dupliqués.

APG (ARIA Authoring Practices Guide)

  • C’est quoi ? Un guide officiel du W3C avec patrons de conception et raccourcis clavier attendus pour chaque widget (onglets, menu, liste, slider…).
  • À retenir côté clavier :
    • Onglets : flèches gauche/droite pour changer d’onglet, Home/End, Tab vers le panel.
    • Menu/Menu bar : flèches pour parcourir, Esc pour fermer.
    • Accordéon : Enter/Espace pour ouvrir, flèches pour naviguer.
    • Dialog : focus piégé à l’intérieur, Esc ferme, restitution du focus.

Anti-patterns fréquents

  • role="button" sur un <div> sans gestion clavier (Enter/Espace) → utilisez <button>.
  • aria-hidden="true" sur un élément focusable (devient invisible au lecteur d’écran mais tabulable → incohérent).
  • aria-expanded sans lier le panneau avec aria-controls.
  • Icône seule cliquable sans nom accessible (aria-label="Supprimer").
  • Cumuler aria-label et aria-labelledby (le label gagne, le texte peut être ignoré).
  • role="presentation"/aria-hidden sur du contenu informatif.

Test & debug ARIA (vite fait)

  • DevTools (Accessibility Tree) : Chrome/Firefox → voir nom, rôle, état.
  • Audit : axe DevTools, Lighthouse (rubrique Accessibilité).
  • Vérif clavier : Tab/Shift+Tab, Enter/Espace, Esc.
  • Lecteurs d’écran : NVDA (Windows), VoiceOver (macOS).
