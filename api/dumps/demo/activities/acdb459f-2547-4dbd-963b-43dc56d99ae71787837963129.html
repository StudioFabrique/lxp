Définition. La séparation des préoccupations vise à isoler des responsabilités distinctes pour éviter qu’elles se parasitent : présentation, orchestration, domaine, infrastructure, transverse (logging, sécurité, cache…).

Ce que cela change concrètement.

  • Lisibilité : chaque couche répond à une question précise (ex. “Quelle règle métier ?” vs “Comment persister ?”).
  • Testabilité : on teste le domaine sans I/O, l’infrastructure avec des doubles, les intégrations de bout en bout séparément.
  • Évolutivité : on remplace un adapter (DB, broker, API) sans toucher au cœur.

Bonnes pratiques pour l’appliquer.

  • Architecture hexagonale :
    • Domaine : entités, invariants, services métier (sans dépendance technique).
    • Application : use-cases, transactions, orchestration.
    • Adapters : HTTP, base de données, messaging, cache.
  • Dépendances dirigées vers l’intérieur (domaine), jamais l’inverse.
  • Cross-cutting : traiter via middleware, décorateurs, policies ; éviter de les disséminer dans le domaine.
  • Composition root (injection de dépendances) unique pour câbler les adapters.

Mauvaises odeurs fréquentes.

  • Logique métier dans des contrôleurs ou des repositories.
  • Couche “service” devenue transit (ne fait qu’appeler d’autres couches sans valeur).
  • Références directes à l’ORM dans le domaine.
