1) Limites techniques (écosystème & compatibilité)

  • Support inégal des aides techniques : différences NVDA/JAWS/VoiceOver ; mobile ≠ desktop.

  • Composants custom & ARIA : ARIA ne crée pas le focus ni les comportements clavier ; divergence de prise en charge.

  • SPA & navigation : changements de page sans rechargement mal annoncés (focus, titre, aria-live).

  • Libs tierces : cartes, lecteurs vidéo, graphiques, SDK “fermés” difficiles (ou impossibles) à rendre accessibles.
    Mitigation : privilégier le natif, choisir des librairies auditées, tester tôt sur plusieurs AT et plateformes.

2) Limites UX & design (contraintes esthétiques vs usage réel)

  • Contrastes de marque parfois trop faibles ; focus visible “pas brandé” rejeté.

  • Interactions gestuelles (drag & drop, hover-only) excluent clavier/écran tactile.

  • Animations/mouvements (parallax) gênent certaines personnes (vestibulaire).
    Mitigation : tokens de design pour contrastes, états focus stylés, alternatives clavier, respect de prefers-reduced-motion.

3) Limites de contenu (au-delà du code)

  • Textes trop complexes ; jargon ; langues multiples mal gérées.

  • Alt text et transcriptions manquants ou de mauvaise qualité.

  • Contenu généré par les utilisateurs : on ne contrôle pas toujours l’accessibilité.
    Mitigation : guides éditoriaux, contrôle de qualité (alt obligatoires), modération et modèles pour UGC.

4) Limites réglementaires & de conformité

  • Conformité ≠ utilisabilité : passer AA ne garantit pas une bonne UX pour tous (surtout cognitif).

  • Portée légale : périmètre variable (public/privé), versions WCAG/RGAA qui évoluent.

  • Documents “accessibles” superficiels (attestations sans preuves).
    Mitigation : audits hybrides (automatique + manuel + tests utilisateurs), preuves (issues, PR, rapports), revues continues.

5) Limites des tests & outils

  • Outils automatiques ne détectent qu’une partie des problèmes (relations, intentions, logique).

  • Variabilité des lecteurs d’écran (verbalisation différente d’un même widget).

  • Environnements : zoom 200–400 %, thèmes système, contraste élevé, modes sombres.
    Mitigation : inclure tests clavier, lecteurs d’écran, zoom fort, thèmes forts ; scenarios “happy/sad paths”.

6) Limites organisationnelles (temps, budget, compétences)

  • Shift-right (prise en compte tardive) → dette chère à rembourser.

  • Manque de compétences dans l’équipe & chez les prestataires.

  • Dépendances bloquantes : design system non accessible, composants privés.
    Mitigation : shift-left (critères a11y dans les US), Design System accessible, revues d’accessibilité en CI, formation.

7) Cas intrinsèquement difficiles

  • Visualisation de données (charts complexes), cartes interactives, canvas/WebGL, jeux 2D/3D.

  • Temps réel (trading, chat), infinite scroll, CAPTCHA.
    Mitigation : alternatives textuelles/CSV, résumés (insights clés), navigation clavier, paginations, CAPTCHA invisibles/alternatives, canaux de support.

8) Contexte utilisateur & matériel

  • Matériel ancien, faible débit, actions à une main sur mobile, contrastes système.

  • Préférences OS parfois non exposées au web, ou mal prises en compte.
    Mitigation : performance (poids, LCP), progressive enhancement, tests sur devices réels.
