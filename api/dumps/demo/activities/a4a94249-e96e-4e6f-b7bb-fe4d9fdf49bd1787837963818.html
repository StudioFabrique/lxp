L’architecture traditionnelle s’appuyait souvent sur une conception très en amont (BUFD, Big Upfront Design), où les architectes tentaient d’anticiper toutes les exigences futures avant l’implémentation.

Mais dans le monde actuel, qui évolue rapidement — marchés changeants, réglementations en évolution, technologies émergentes — cette approche échoue.

À la place, nous avons besoin d’une architecture évolutive :

  • Des systèmes conçus pour s’adapter au changement de manière robuste et progressive.
  • Une priorité donnée à l’évolution incrémentale plutôt qu’aux réécritures massives.
  • Des principes qui permettent aux systèmes de grandir sans devenir fragiles.

Qu'est-ce l’architecture évolutive ?

L’architecture évolutive (“evolutionary architecture”) part d’une idée simple : on considère le changement comme un besoin de premier ordre. Au lieu de “figer” une architecture au départ, on conçoit le système pour qu’il puisse évoluer par petites étapes, de manière guidée, sur plusieurs dimensions (technique, données, déploiement, organisation, etc.).

Qualités clés :

  • Modularité – de petites unités évoluent de façon indépendante.
  • Tests automatisés – un filet de sécurité pour un changement continu.
  • Observabilité – surveiller comment le système se comporte en production.
  • Fonctions de fitness – des critères mesurables pour valider les objectifs d’architecture.

Ces quatre “qualités clés” sont des capacités opérationnelles qui rendent le changement fréquent possible sans casser le système. Elles sont liées : modularité réduit l’impact des changements, les tests donnent la sécurité, l’observabilité donne la réalité en prod, et les fitness functions rendent les objectifs d’architecture vérifiables.

Modularité
  • Idée : découper le système en unités cohérentes et relativement autonomes (modules, services, bounded contexts) avec des frontières nettes.
  • Pourquoi c’est critique : si tout est couplé, chaque modification devient un “risque global” et coûte cher (coordination + tests + régressions). Avec de bons boundaries, un changement reste local.

Concrètement, ça implique :

  • Ownership clair : une équipe “possède” un module/service et ses données.
  • Interfaces stables : API/événements versionnés, contrats explicites.
  • Dépendances contrôlées : pas d’accès direct à la DB d’un autre service, pas de “import” entre modules interdits.
  • Cohésion : un module fait une chose métier, pas un mélange.

Tests automatisés
  • Idée : fournir un filet de sécurité rapide et fiable pour modifier le code en continu.
  • Pourquoi c’est critique : l’architecture évolutive suppose des changements fréquents. Sans tests, tu ralentis (peur de casser) ou tu casses souvent.

Couches utiles (et ce qu’elles protègent) :

  • Tests unitaires : invariants métier, logique locale (rapides).
  • Tests d’intégration : DB, cache, dépendances (plus lents).
  • Tests de contrat : compatibilité API/événements entre producteurs/consommateurs.
  • Tests end-to-end : parcours critiques (peu nombreux, coûteux mais indispensables).
Observabilité
  • Idée : comprendre ce que fait réellement le système en production (pas seulement “ça tourne”).
  • Pourquoi c’est critique : en environnement distribué, les bugs et dégradations sont souvent invisibles en dev. L’observabilité sert à détecter, diagnostiquer et piloter.

Les 3 piliers :

  • Logs : événements et contexte (corrélation, erreurs).
  • Metrics : SLI/SLO (latence P95/P99, taux d’erreurs, saturation CPU/mémoire, backlog de queue).
  • Traces distribuées : suivre une requête à travers plusieurs services (où est la latence ? qui casse ?).
Fitness functions

  • Idée : rendre testables les objectifs d’architecture (les “-ilities”). Une fitness function est une vérification automatisée (ou semi-automatisée) qui mesure un critère d’architecture et échoue si le système dérive.
  • Pourquoi c’est critique : sinon, “maintenabilité”, “sécurité”, “scalabilité” restent des slogans. Avec une fitness function, c’est un garde-fou continu.

Exemples concrets (très utilisés) :

  • Performance : “P95 < 200 ms sur /checkout” (test de perf en CI + monitoring en prod).
  • Résilience : “le service tient si la dépendance X répond en 2s” (chaos testing / tests de timeout).
  • Couplage : “interdiction d’appels directs vers la DB d’un autre domaine” (règles d’architecture).
  • Déployabilité : “déploiement < 10 min, rollback < 5 min” (mesuré via pipeline).

Principes

Principe 1 : le pattern « Strangler Fig » (figuier étrangleur)

Remplacer un système legacy de manière incrémentale en construisant de nouvelles fonctionnalités autour de lui, puis en “étranglant” progressivement l’ancien système.

Pourquoi utiliser cette méthode?

  • Les réécritures “big bang” échouent souvent.
  • Une migration incrémentale réduit le risque.

Exemple : système legacy de gestion des commandes

Sans Strangler :
- réécrire tout le monolithe → des années d’effort, très risqué.
Avec Strangler :
- Router les nouveaux appels API /orders vers un nouveau service.
- Le legacy continue de servir les anciennes fonctionnalités.
- Déplacer progressivement le trafic jusqu’à retirer l’ancien système.


Principe 2 : Continuous Delivery (livraison continue)

L’évolution architecturale nécessite des déploiements rapides et sûrs.

  • Des releases fréquentes réduisent la taille des lots de changements.
  • L’automatisation (CI/CD) garantit la cohérence.
  • Les rollbacks minimisent le risque.

Pratiques

  • Tests automatisés à tous les niveaux.
  • Infrastructure as code
  • Déploiements canary et feature flags.

Principe 3 : Fitness Functions

Des contrôles automatisés qui mesurent si le système respecte ses objectifs d’architecture.
Exemples :

  • Temps de réponse < 200 ms.
  • 99,99 % de disponibilité.
  • Aucune dépendance cyclique.

Les fitness functions garantissent que l’évolution n’érode pas les qualités clés.
