Définition. La dette technique, c’est un écart volontaire ou accidentel entre l’état actuel et un état plus sain. Elle “produit des intérêts” : chaque changement coûte plus cher et casse plus souvent si la dette n’est pas gérée.

Typologie utile.

  • Dette de code : duplication, complexité accidentelle, noms confus.
  • Dette d’architecture : mauvaises frontières, base partagée, couplage fort.
  • Dette de tests : couverture insuffisante, tests fragiles (flaky), absence de tests de contrats.
  • Dette d’outillage : builds lents, CI peu fiable, manque d’observabilité.
  • Dette de sécurité : secrets mal gérés, libs vulnérables, droits trop larges.
  • Dette de données : schémas non versionnés, migrations manuelles hasardeuses.

Quand l’accepter, quand la rembourser.

  • Intentionnelle (stratégique) : on l’assume à court terme pour livrer une valeur critique, avec un plan de remboursement clair.
  • Accidentelle : on la réduit dès qu’elle nuit à la compréhension, à la stabilité ou à la vitesse d’évolution.

*Gérer la dette avec discipline.

  • Rendre visible : nommer, décrire l’impact, tracer où elle se situe.
  • Remboursement continu : petites améliorations à chaque changement (“Boy Scout Rule”) et refactors ciblés.
  • Sécuriser les refactors : tests de régression, feature flags, déploiements progressifs.
  • Décisions explicites : consigner dans des ADRs quand une dette est acceptée (contexte, horizon de retrait).

Signaux d’alerte.

  • Changements “simples” qui exigent de toucher de nombreuses zones.
  • Corrections qui cassent des parties éloignées.
  • On “n’ose plus” modifier un module sans craindre des effets secondaires.
